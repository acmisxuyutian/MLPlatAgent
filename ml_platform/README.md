# MLPlatAgent Platform Extension Guide

[中文](README_ZH.md)

The `ml_platform` package isolates the MLPlatAgent core from implementation differences across machine learning platforms.

The Planner decomposes a user request into machine learning tasks. The Executor selects components from the active platform's catalog and generates workflow operations. The platform Action then translates those operations into native API, SDK, or workflow-file operations.

To add a platform, a developer only needs to provide:

- a component catalog in `widgets.json`;
- a workflow adapter implemented as `PlatformAction`;
- a platform configuration named `<PLATFORM>_CONFIG`;
- the platform runtime and dependencies.

The Agent core continues to use the same process-wide object:

```python
from ml_platform.actions import action_agent
```

In most cases, adding a platform does not require changes to the Planner, Executor, MLAgent, or the shared Action factory.

## Extension Boundary

`PlatformAction` is the adapter between the Agent and a machine learning platform. It is responsible for:

- validating its own platform configuration;
- connecting to or loading the active workflow;
- translating common workflow operations into native platform operations;
- converting Agent-facing parameters into native component parameters;
- creating any auxiliary nodes, links, or metadata required by the platform;
- converting the native workflow into the common workflow snapshot;
- keeping credentials, connection objects, and other private state out of the Agent-facing interface;
- returning clear errors for unsupported components, parameters, or connections.

A platform adapter may perform multiple native steps for one Agent operation, but it must preserve the common Action contract.

## Quick Start: Add a Platform

The following example uses `my_platform` as the platform name:

1. Create `ml_platform/my_platform/`.
2. Add `widgets.json` and describe every component and parameter exposed to the Agent.
3. Add `actions.py` and export `PlatformAction(Action)`.
4. Add `MY_PLATFORM_CONFIG` to the root `config.py`.
5. Validate the configuration, load the active workflow, and implement the seven Action methods.
6. Keep platform-specific dependencies and state inside the platform package.
7. Set `PLATFORM = "my_platform"` and run the root `run.py`.

Once these conventions are satisfied, the platform can be integrated without changing the Agent's core orchestration logic.

## Directory and Discovery Conventions

The platform name must match its directory under `ml_platform` and contain only lowercase letters, numbers, or underscores.

```text
ml_platform/
├── action.py
├── actions.py
├── README.md
├── README_ZH.md
└── my_platform/
    ├── actions.py
    ├── widgets.json
    └── other platform-specific modules
```

The shared files have the following responsibilities:

- `action.py` defines the abstract interface and common state.
- `actions.py` reads `config.py`, loads the selected platform, and creates the global `action_agent`.
- `<platform>/actions.py` implements native workflow operations.
- `<platform>/widgets.json` declares the platform capabilities exposed to the Agent.

Every platform module must export:

```python
class PlatformAction(Action):
    ...
```

The shared factory discovers the class by convention:

```python
ml_platform.<platform>.actions.PlatformAction
```

No platform-specific branch needs to be added to the factory.

## Common Action Contract

Every `PlatformAction` must inherit from `ml_platform.action.Action` and implement the following methods. Mutation methods receive one argument dictionary, matching the call format generated by the Executor.

| Method | Required input | Responsibility |
| --- | --- | --- |
| `add_node` | `widget_name`, `node_name` | Create a component node and return its node ID |
| `delete_node` | `node_id` | Delete a node and its required platform state |
| `update_node_params` | `node_id`, `widget_name`, `node_params` | Update Agent-facing node parameters |
| `add_edge` | `source_node_id`, `target_node_id` | Create a connection and return its edge ID |
| `delete_edge` | `edge_id` | Delete a connection |
| `get_workflow` | None | Return the common workflow snapshot |
| `clear_workflow` | None | Clear the workflow selected by the platform configuration |

The base `Action` class already provides component loading and validation, component indexes, the task-level component allowlist, token and timing statistics, layout state, `reset()`, and controlled `execute_command()` dispatch. Platform implementations should reuse these capabilities.

Minimal implementation:

```python
from typing import Any, Mapping

from ml_platform.action import Action


class PlatformAction(Action):
    def __init__(self, platform_config: Mapping[str, Any]):
        super().__init__(
            platform_config,
            platform_name="my_platform",
        )
        # Validate configuration and load the active workflow.

    def add_node(self, args):
        ...

    def delete_node(self, args):
        ...

    def update_node_params(self, args):
        ...

    def add_edge(self, args):
        ...

    def delete_edge(self, args):
        ...

    def get_workflow(self):
        ...

    def clear_workflow(self):
        ...
```

Failures should raise `ActionError` or a platform-specific subclass with a clear explanation. An adapter must not silently ignore a failure, switch platforms, or substitute an undeclared component.

## Component Catalog

The Executor uses the active platform's `widgets.json` as the source of component capabilities and parameter definitions.

Each component must contain at least:

```json
{
  "widget_name": "Classifier",
  "widget_id": "platform-native-component-id",
  "description": "Train a classification model.",
  "type": "model",
  "params": [
    {
      "name": "max_depth",
      "type": "int",
      "default": 5,
      "description": "Maximum model depth."
    }
  ]
}
```

Field requirements:

- `widget_name`: the unique component name used by the Agent;
- `widget_id`: the native component identifier interpreted by `PlatformAction`;
- `description`: the capability description used during component retrieval and selection;
- `type`: the machine learning task type associated with the component;
- `params`: the Agent-facing parameter definitions;
- every parameter must define `name`, `type`, `default`, and `description`.

`widget_name` must match the names accepted by `PlatformAction` and returned by `get_workflow()`. Additional native metadata may be included when needed, but credentials must never be stored in the catalog.

When native parameters differ from Agent-facing parameters, the conversion belongs in `PlatformAction`. The Planner and Executor should not need to understand native platform objects.

## Common Workflow Snapshot

`get_workflow()` must return a structure that can be serialized by `json.dumps`:

```json
{
  "nodes": [
    {
      "node_id": "1",
      "widget_name": "Data Source",
      "node_name": "Training Data",
      "node_params": {
        "dataset": "customer_data"
      }
    },
    {
      "node_id": "2",
      "widget_name": "Classifier",
      "node_name": "Classification Model",
      "node_params": {}
    }
  ],
  "edges": [
    {
      "edge_id": "1",
      "source_node_id": "1",
      "target_node_id": "2"
    }
  ]
}
```

Snapshot requirements:

- `nodes` and `edges` must always exist and must be lists;
- node and edge IDs must refer to each other consistently within a snapshot;
- `widget_name` must use the Agent-facing name declared in `widgets.json`;
- `node_params` must use Agent-facing parameter names and values;
- tokens, passwords, native connection objects, and non-serializable values must not be included;
- auxiliary nodes created by the adapter must appear when they affect subsequent workflow orchestration.

## Configuration and Startup

Platform selection and user configuration belong in the root `config.py`. Command-line parameters are not used:

```python
PLATFORM = "my_platform"

MY_PLATFORM_CONFIG = {
    "workspace": "",
}
```

The configuration name must follow this convention:

```text
<PLATFORM.upper()>_CONFIG
```

The factory reads only the selected platform configuration and passes that mapping to `PlatformAction`. The adapter validates its own required fields. Configuration and dependencies for unselected platforms must not participate in initialization.

`action_agent` is a process-wide singleton. Restart the Python process after changing `PLATFORM` or its configuration.

The project must be started through the root entry point:

```powershell
python .\run.py
```
